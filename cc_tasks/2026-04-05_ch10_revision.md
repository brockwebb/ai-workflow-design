## Part C: Knowledge Graph Treatment (Clusters C2 — HIGH priority)

### What

Add a new section to Ch 10 that fulfills the forward references from Ch 6 ("Chapter 10 provides the implementation guidance") and Ch 9 (graph-based state externalization as SFV countermeasure infrastructure). This resolves the three-chapter broken forward reference cascade flagged in C2.

### Where

Insert a new `##`-level section **after** "The Graph-of-Artifacts Pattern" and **before** "Shared Vocabulary as Infrastructure." Title: `## When Pipeline State Is Graph-Shaped` (or similar — the title should signal design choice, not technology).

### Content guidance per design note

The design note (`docs/design_note_knowledge_graphs_as_pipeline_state.md`) specifies the Ch 10 scope. This section should cover:

1. **The design choice framing (connecting from Ch 6 seed):** Ch 6 established that some state is tabular (relational) and some is graph-shaped (typed relationships). This section provides the implementation guidance for graph-shaped state.

2. **What graph-shaped state looks like in practice:**
   - Artifact dependencies (chapter depends on dataset; result generated by script)
   - Decision provenance (decision A supersedes decision B; decision A was informed by evidence C)
   - Typed relationships (informs, depends_on, tracks, supersedes) — these are the edges the system traverses for impact analysis and staleness propagation
   - State transitions as first-class operations on nodes, not implicit context window position

3. **Seldon as worked example (pattern, not tutorial):**
   - Artifact nodes with types and state machines
   - Relationship types and what queries they enable
   - Session orientation as graph reconstitution (the `seldon go` pattern — reconstructing working context from the graph, not from memory)
   - Cascade impact analysis as graph traversal
   - Frame every Seldon feature as a transferable pattern: "This system does X. The pattern is Y. Your system needs Y regardless of implementation."

4. **Pragmatics as counterpoint:**
   - Deterministic graph lookups vs. probabilistic retrieval (RAG)
   - The 91.2% vs 74.6% pipeline fidelity comparison from Ch 9
   - The insight: when you need a specific expert judgment, not a similar one, graph traversal outperforms embedding similarity

5. **The relational-to-graph migration path:**
   - Your audience knows SQL. Show them what Cypher (or equivalent) gives them that SQL doesn't: path queries, variable-length traversals, pattern matching across relationship types.
   - "If you're already doing JOINs across three or more tables to answer provenance questions, you have a graph you haven't named yet."

6. **Practical tradeoffs:**
   - When to use relational: simple tabular state, run logs, parameter snapshots
   - When to use graph: relationship-rich state, provenance chains, impact analysis
   - When to use both: most real pipelines (and Seldon itself uses both — event log in files, graph for queries)
